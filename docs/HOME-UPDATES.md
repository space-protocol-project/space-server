# Подготовка обновления домашнего сервера

Штатный выход по SIGINT/SIGTERM и EOF управляющего процесса завершает оба HTTP-входа параллельно: подписки отменяются сразу, принятые обычные RPC получают общий срок 10 секунд. Затем останавливаются планировщик копий, публичные сетевые ресурсы, внутренний gRPC и пул (до 5 секунд каждый), после них собственная PostgreSQL через `pg_ctl -m fast -w -t 15` (команда ограничена 20 секундами). Превышение срока возвращает ошибку, а не успешное подтверждение. Управляющий процесс ждёт EOF/выход и проверяет отсутствие `postmaster.pid`; жёсткое завершение не заменяет эту процедуру.

Кнопка обновления и исполнитель добавлены в новое приложение. Новый публичный выпуск runtime пока не закреплён. Команды ниже предназначены для локального управляющего процесса и диагностики; они не заменяют проверку архива и сериализацию операций.

`-home-check -home-runtime RUNTIME -home-data DATA` проверяет чистую остановку, существующий сертификат, запускает только loopback PostgreSQL, проверяет совместимость схемы без миграций и останавливает базу. `-home-migrate` выполняет тот же предварительный контроль, затем транзакционные миграции и повторную проверку схемы. JSON содержит serverId, tlsFingerprint, schemaVersion, targetSchemaVersion и postgresMajor. Успех возвращается только после остановки PostgreSQL. Публичные порты не открываются. `-home-stopped` проверяет чистую остановку без обращения к схеме, чтобы разрешить восстановление повреждённой базы без попытки мигрировать её снова.

`space-server -runtime-info` печатает JSON: format=1, protocolVersion, schemaVersion, postgresMajor, os и arch. Команда не подключается к базе и не открывает слушающие порты. Сборщик включает тот же JSON в runtime-info.json и проверяет соответствие основной версии PostgreSQL комплекту. Метаданные получают доверие только вместе с проверенным архивом; сам JSON не является подписанным манифестом.

`space-server -check-database` использует SPACE_DATABASE_URL для уже доступной домашней PostgreSQL. Это отдельный процесс без HTTP/gRPC и без вызова инициализации хранилища. За 15 секунд он проверяет в read-only/repeatable-read транзакции PostgreSQL 17, непрерывную историю миграций и их контрольные суммы, наличие server ID и корректного серверного ключа. Вывод содержит schemaVersion, targetSchemaVersion, postgresMajor и serverId; пароль и ключ не выводятся. Несовместимость возвращает ненулевой код завершения. Версия 9 старого выпуска v0.1.0 может быть проверена новым сервером без применения миграций 10/11. Неизвестная, пустая, повреждённая или более новая история блокируется.

Проверка не заменяет блокировку операций и окончательную проверку после остановки: работающая база могла измениться после снимка. Перед миграциями управляющий процесс должен закрыть внешний вход, штатно остановить сервер, подготовить и проверить согласованную резервную копию и повторно проверить совместимость. После миграций откат бинарного файла без восстановления базы может быть невозможен.

StartDatabase также проверяет реальную версию postgres --version и PG_VERSION до создания пароля, изменения конфигурации и запуска PostgreSQL. Каталог существующей базы без PG_VERSION или с пустой версией не считается новой установкой. Смена основной версии требует отдельной процедуры pg_upgrade или выгрузки/восстановления.

## Резервная копия и проверяемое восстановление

Управляющий процесс должен сериализовать эти операции с запуском и остановкой. Команды не открывают сетевые порты и не запускают PostgreSQL. Перед копированием и после него проверяются отсутствие postmaster.pid, версия PostgreSQL и состояние `shut down` из pg_controldata. Работающая или аварийно остановленная база отклоняется. Ссылки, внешние tablespace и специальные файлы не поддерживаются.

```text
space-server -home-runtime RUNTIME -home-data HOME/data -home-backup BACKUP
space-server -home-runtime RUNTIME -home-restore BACKUP -home-restore-to RESTORED_HOME
```

Назначение должно быть новым каталогом вне источника. Копия содержит `data/`, включая базу, пароль PostgreSQL, серверные ключи и TLS-сертификат. Если рядом с исходным data присутствуют config.json и active-runtime.json, они тоже сохраняются. Пустые каталоги PostgreSQL сохраняются. backup.json содержит список каталогов и SHA-256 каждого файла; пропущенные, дополнительные и изменённые файлы блокируют восстановление. Это проверка повреждения, а не защита от злоумышленника, заменившего также манифест. Копия содержит секреты в открытом виде: каталог создаётся с ограниченными Unix-правами, на Windows наследуется ACL родительского каталога. Шифрованный перенос и настройка отдельного Windows ACL — следующие задачи.

Результат публикуется переименованием подготовленного каталога после полной проверки. Восстановление создаёт RESTORED_HOME/data и сохранённую конфигурацию; текущая база и исходная копия не заменяются. Для запуска восстановленных данных home-data указывает RESTORED_HOME/data. Манифест фиксирует ОС, архитектуру и основную версию PostgreSQL; другая платформа отклоняется. Это не перенос между ОС/архитектурами. Перед активацией управляющий процесс ещё должен проверить совместимость схемы и идентичность, а также организовать журнал переключения/возобновления после сбоя.

CI комплекта runtime проверяет: отказ копирования работающей базы, чистую остановку, создание и проверку копии, восстановление в новый каталог, повторное открытие PostgreSQL и сохранение server ID, сертификата, конфигурации и пользовательской записи.
