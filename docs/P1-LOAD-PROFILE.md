# Ограниченная нагрузка P1

Профиль фиксируется до запуска. Три независимых Linux CI runner, каждый с собственной PostgreSQL 17.11. Фазы по 300 секунд: 1, 2 и 8 клиентов; первые 60 секунд каждой фазы исключаются из распределений. Случайность не используется: seed отсутствует, расписание детерминировано номером операции. После каждой операции пауза 20 мс, квоты и deadline исполнителя не меняются.

Набор: одна установка, 360 заранее зарегистрированных экземпляров для трёх фаз и восьми клиентов (15 слотов на клиента), контрольный `demo`, независимый `other` на другом канале и `quota`. Каждые 20 секунд клиент переходит на следующий слот. Первый успешный вызов фиксированного WASM-плана переводит ревизию 0 → 1, пишет один ключ и одно событие. Последующие команды с тем же ключом сверяют квитанцию. Это ограниченный набор, без удаления квитанций или данных во время нагрузки.

Цикл из восьми операций: query, уникальная команда либо её повтор, replay, конфликт байтов payload, конфликт ревизии, заранее отменённый query, stateless-команда и query независимого экземпляра. До первой успешной записи конфликт payload заменяется повтором исходной команды. Ожидаемые коды: OK, ResourceExhausted при занятом бюджете; AlreadyExists для конфликта payload; Aborted для ревизии; Canceled для отмены. Другие ошибки проваливают приёмку. Отмена уже исполняющегося вызова проверяется отдельными детерминированными тестами ядра.

До нагрузки проверяются ACL и блокировка участника. Во время каждой фазы повторяется отзыв ACL/членства и проверяется PermissionDenied. Владелец продолжает независимые запросы; гонки отзыва между WASM и COMMIT остаются обязательной отдельной матрицей ядра. До нагрузки `quota` явно заполняется 1024 тестовыми квитанциями: следующая запись отклоняется, команда `other` успешна. Эти строки сохраняются до конца; финальная сверка отдельно исключает подготовленные квитанции.

Все запросы проходят настоящий gRPC, сессии ядра, dispatcher и ProcessHost; WASM компилируется/исполняется отдельным процессом. Бюджет ProcessHost 512 МиБ, worker 256 МиБ, deadline 2 с. Старый внутренний профиль регистрации разрешает только собственные данные и `note_changed`; гостю не выдаются ядро, сеть или каталог устройства. Полный manifest со stateless-формами проверяется отдельным профилем и не используется для обхода запрета мутаций.

`requests.jsonl` содержит фазу, клиента, операцию, код, задержку и признак прогрева. `summary.json` содержит p50/p95/p99 и число запросов в секунду по фазе/операции/коду. `resources.jsonl` каждые 5 секунд фиксирует RSS/HWM процесса тестового сервера, cgroup CPU/память/OOM/процессы/резервирование, суммарное ожидание получения соединения пула и размер данных/квитанций/outbox. Ожидание пула не объявляется временем блокировок SQL; RSS включает gRPC-клиентов и race-инструментацию в том же процессе.

После остановки клиентов проверяются нулевые активные вызовы/резервирование/процессы, отсутствие дочерних cgroup, точное равенство числа успешных первых команд ревизиям, данным, квитанциям и событиям, контрольная команда и освобождение пула. Публикуются исходные значения, а не SLA продукта. Неуспешный прогон требует исправления и повторной полной приёмки.

Перед каждой пятиминутной фазой выполняется настоящий challenge/signature вход тем же владельцем и устройством. Это не продление строки сессии в БД: прежний десятиминутный срок жизни сохраняется. Первый прогон 42993902053 выявил истечение исходной сессии на третьей фазе и не засчитывается; повтор выполняет все три фазы заново.
