# Серверный поиск и история 100 000 сообщений

Статус: следующий локальный срез v0.5, не выпущен. Контракты RPC не меняются. Миграция 021 повышает схему runtime до 21.

## Поиск

Частичный GIN-индекс `contents_search_terms_v1` содержит двух- и трёхсимвольные подстроки неудалённых обычных сообщений. Запрос из двух Unicode-символов использует биграммы, более длинный — триграммы. Расширения PostgreSQL, включая pg_trgm, не нужны. После отбора индексом `strpos` повторно проверяет буквальную подстроку: набор грамм не является доказательством совпадения. `%`, `_`, пробелы, пунктуация, китайский текст и эмодзи остаются обычным текстом.

Нормализация регистра закреплена в `space_search_fold_v1` по таблице Unicode Go, без зависимости от локали PostgreSQL. SQL-функции используют разобранные при создании тела RETURN: зависимости привязаны к объектам своей схемы, а не заново ищутся по search_path при работе индекса. Тест сверяет всю таблицу с unicode.ToLower текущего Go; при её изменении нужна новая версия функции/индекса и миграция, нельзя незаметно менять IMMUTABLE-функцию действующего индекса.

Вычисляемый хранимый столбец search_text содержит нормализованный текст обычного сообщения. PostgreSQL сам обновляет его и индекс при создании, правке и удалении; приложение не поддерживает вторую копию вручную. Точная проверка совпадений читает этот столбец, чтобы частые запросы не повторяли дорогую нормализацию для каждой найденной строки. Исходный текст в RPC остаётся прежним. Миграция строит индекс по существующим строкам. Авторизация и ACL проверяются перед запросом каждой страницы; лимит 50 результатов, граница sequence и трёхсекундный бюджет сохранены. MLS-поиск на сервере по-прежнему запрещён.

## Обновление

Индекс создаётся внутри обычной транзакционной миграции при запуске runtime. Содержимое исходных сообщений, идентичность, настройки, очереди и курсоры событий сохраняются. Добавление GENERATED STORED физически перестраивает таблицу и добавляет нормализованную копию обычного текста; это учитывается вместе с местом для индекса. Сборка индекса занимает время и дополнительное место; на длительность обновления влияет объём текста. Это не фоновое CREATE INDEX CONCURRENTLY. Старый runtime не должен открывать базу новой схемы — действует обычная проверка совместимости и восстановление резервной копии при откате.

## Проверка

`TestSearchAndHistory100000` использует отдельную тестовую схему PostgreSQL. В ней создаются 100 000 записей и событий, затем выполняется настоящая миграция 20 → 21 поверх этих данных. Наполнение сделано массовым SQL для скорости подготовки; поиск и чтение всех 1000 страниц идут через настоящий авторизованный gRPC ContentService. Это не проверка 100 000 последовательных отправок Flutter-клиентом и не сквозной прогон интерфейса.

Проверяются пять редких совпадений без учёта регистра, EXPLAIN ANALYZE с индексом без полного Seq Scan, Unicode-таблица, повторное открытие сервера с прежней идентичностью, обновление индекса после правки/удаления, идемпотентный повтор CreateContent, граница событий и чтение 100 000 записей без пропусков, дублей и сдвига после конкурентной вставки. Отдельные тесты проверяют ACL, MLS, страницы, двухсимвольные запросы, китайский текст, эмодзи, буквальные знаки и ложноположительный набор триграмм.

Замеры выполняются на Windows/PostgreSQL 17 с короткими сообщениями и тёплым кэшем. Они не являются гарантией для длинных текстов, частых запросов и любой машины. В тест добавлено чередование частых и редких запросов после прогрева prepared statements: именно оно выявило дорогую нормализацию повторных совпадений и обосновало вычисляемый хранимый столбец. Поиск сохраняет трёхсекундный бюджет.


Полный прогон также выявил нестабильную очистку временных файлов свидетеля сети на Windows. В его тестовой fixture добавлена ограниченная повторная очистка собственного TempDir перед стандартной очисткой testing; постоянная ошибка остаётся ошибкой. Пять повторных прогонов пакета home после исправления прошли. Производственная логика свидетеля не менялась.

Замер окончательного алгоритма: подготовка 100 000 строк и событий — 6,22 с; миграция готовой истории — 33,48 с; редкий SQL-запрос — 0,115 мс; авторизованный поиск через RPC — 6,50 мс; чтение 1000 страниц — 2,24 с. Чередование 12 частых и редких запросов после прогрева планов прошло с прежним трёхсекундным бюджетом. Замер взят из TestSearchAndHistory100000, а не из интерфейса Flutter.

Окончательная проверка: go test ./... -count=1 с настоящей временной PostgreSQL прошёл во всех пакетах (postgres — 124,9 с), go vet ./... прошёл. Проверка обновления схемы 12 сверяет все прежние поля и отдельно ожидаемые значения нового поискового столбца. Изменения индекса/схемы 21 и исправление тестовой очистки пока локальные; пользовательская база не менялась.
